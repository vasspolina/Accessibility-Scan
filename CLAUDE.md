# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

There is no root package: each of `backend/`, `widget-business/`, `widget/` and `accessible-web-design/` has its own `package.json` and lockfile, and commands run from inside that directory. Node 24 (`backend` declares `engines >=24`; CI uses 24). Node is not on the shell's PATH here: the local runtime is `.tools/node/bin/` (gitignored), which also holds `npm`, `npx` and `railway`. `.claude/launch.json` starts the dev servers through it: `backend` (:8787), `widget-business` (:5174), `widget` (:5173), `accessible-web-design` (:5175).

```bash
# backend/
npm run dev                         # tsx watch src/server.ts, API on :8787
npx tsc --noEmit                    # CI runs types first
npm test                            # vitest run (~60 files in test/)
npx vitest run test/scoring.test.ts # one file; add -t "name" for one test
npm run build                       # tsc to dist/
npm run build:widget-business       # builds ../widget-business, copies the bundle into public/
node dist/cli.js https://example.com   # the a11y-scan CLI (docs/CLI.md: exit 0 ok, 1 threshold missed, 2 scan failed); takes several URLs, --urls, --sitemap; writes --json --sarif --junit --csv --markdown
node dist/mcp.js                       # a11y-scan-mcp, the scanner as an MCP stdio server (docs/MCP.md); stdout is protocol only

# widget-business/
npx vite                            # dev harness on :5174
npx tsc -b && npm test              # types, then vitest
npm run check:reflow                # every fixture state at 320/375px in en/de/es/fr (needs Playwright chromium); see the font caveat under Type
npm run lint:css                    # undefined var(--x) and same-specificity collisions
node scripts/check-styles.mjs       # dead selectors and unstyled classes

# accessible-web-design/  (the public marketing site)
npm run check                       # strict per-locale build, axe on each locale, pseudolocale expansion check
```

CI (`.github/workflows/`) runs only for the package whose path changed: backend is tsc, test, build, then a CLI smoke test from outside the repo; widget is `tsc -b`, test, `check:reflow`, `lint:css`; site is `npm run check`.

**Working on the widget without a backend:** open the dev harness with `?fixture` (stops at the form) or a named state: `?fixture=report`, `?fixture=error`, `?fixture=blocked`, plus `&audience=professional`, `&scope=site`, `&at=<section id>`. `dev-fixture.js` stubs `fetch` for `/api/scan` and `/api/audit`. Copy `backend/node_modules/axe-core/axe.min.js` to `widget-business/axe.dev.js` to axe-scan the rendered widget in place.

`backend/.env` (gitignored) takes `ANTHROPIC_API_KEY`; without it scans still run and the report says the AI layer was skipped. Optional features (mail via `MAIL_API_KEY`, storage via `DB_PATH`) follow the same contract: absent means the feature reports itself as not set up, never a silent failure. All env is validated in `backend/src/config/env.ts`. The self-hosted plain-language model (`LOCAL_LLM_URL`) and the assistive-technology pilot (open to anyone once storage or mail is set up, Report a barrier inside the widget, `widget-business/src/components/BarrierReport.tsx`, since 20 Nov 2026; `backend/public/pilot.html` only sends old links on) follow the same contract; see `docs/PLAIN-LANGUAGE-AND-PILOT.md`.

## Architecture

**Three deployables, one service.** `backend/` is a Fastify server that renders pages in Playwright Chromium and returns a JSON report. It also serves the two embeddable widgets as static files from `backend/public/`. Both widgets are Vite library builds to one self-contained IIFE (React bundled in) that mounts into a shadow root, so host-page CSS cannot leak in. Styles are imported `?inline` and injected into the shadow root (`src/utils/shadowMount.ts`). `@font-face` is ignored inside a shadow root, so `src/index.tsx` declares the fonts at document level, served from the backend.

- `widget-business/` is the product: the plain-language owner's report, with a professional audience toggle over the same scan. Almost all UI work happens here.
- `widget/` is the older technical widget. It has no tests or CI.
- `accessible-web-design/` is the public site, built once per locale by `i18n/build.mjs`.
- `barrierfreeweb/` is the BarrierFreeWeb studio site (home, services and five service pages, accessibility, about) set in the widget's design. `node build.mjs` writes the HTML beside it; the copy lives in `build.mjs`, the look in `styles.css`. The generated pages are committed, so rebuild in the same change as any copy edit.
- `design-system/` is the vendored design system. The widget depends on `design-system/production` as `@verify/design-system` (a `file:` dependency). `system-guide.md` is the spec; the rules in this file override it where they differ.

**The scan pipeline** is `scanUrlToReport` in `backend/src/services/scanPipeline.ts`, called by `POST /api/scan` and by the CLI (`src/cli.ts`). The steps:

1. `assertSafeUrl` (SSRF guard).
2. `render/renderPage.ts` renders at desktop and phone width and runs axe-core. It collects the raw signals every probe needs, such as tab walk, bounding boxes, consent banner and frames, in one page visit.
3. Each `services/<probe>/analyze*.ts` exports a pure `evaluate*` function over those signals. That is why probes are unit-tested without a browser.
4. The optional AI review runs in `aiReview/`.
5. `merge/mergeFindings.ts` merges and filters. Axe, probe and AI findings are fingerprinted and merged, so one fault gives one card and a measured finding beats an AI one. Speculative or contradicted claims are dropped in code.
6. `merge/scoring.ts` scores only provable WCAG A/AA findings. `conformance/` builds the criterion table, with criterion text per language.
7. Thumbnails are cropped last. A second, capped browser visit pictures the findings the render pass could not.

**The overlay note is not a finding.** `services/overlay/analyzeOverlay.ts` names a third-party accessibility overlay on the page (accessiBe, UserWay and others) from the script the page loads and the widget element that script builds. The result is a statement on `meta.overlays` (and `SiteAudit.overlays` for a crawl): no severity, no criterion, no fix, and the score, the counts and the conformance table never see it. It says the findings were measured with the overlay running only when the widget element was in the document; UserWay's loader, for one, does not start for the scanner's user agent. A vendor joins the table only after its script address and its widget element were read on its own documentation or its own site, and its row says which.

**Linked documents are counted, and never scored.** `services/documents/inventoryDocuments.ts` lists the PDFs and Word, Excel and PowerPoint files a page links to (pure, from `pageLinks`), on the report's `documents` field and `SiteAudit.documents` for a crawl. A page scan opens the first two same-origin PDFs (`linkedDocuments.ts`, 12 s for both, each address and redirect through `assertSafeUrl`); a site audit opens none, and the timings behind that are beside `AUDIT_BUDGET_MS` in `routes/audit.ts`. What is found in a linked PDF stays on its inventory entry: never in `findings`, the summary or the score. The reader sees up to three `undecidedChecks` rows (`pdf-linked-not-checked`, `pdf-linked-faults`, `office-linked-not-checked`), worded in the widget by rule id.

Concurrency is bounded by `render/browserPool.ts` (`MAX_CONCURRENT_RENDERS`, default 2, deliberately low because of container memory). Progress streams over `GET /api/scan/progress/:id`, keyed by a client-chosen `progressId`. `POST /api/audit` crawls a site (`crawl/`) and aggregates per-page reports; its candidates are the entry page's links plus the site's sitemap, less what robots.txt disallows (`crawl/sitemap.ts`, pure parsers and one guarded fetcher). `routes/chat.ts` is the report-scoped assistant. `routes/inquiry.ts` is the BarrierFreeWeb studio site's request form: an AI assistant asks up to three questions and the request is mailed to `CONTACT_TO`, never to an address the caller supplies. `backend/public/barrier-ledger.html` (with `barrier-ledger.js`) is the operator's private view of the Report a barrier reports (user's instruction, 21 Nov 2026): it reads `GET /api/pilot/reports` with `ADMIN_TOKEN`, shows each person's words beside the model's draft, and saves a signed Caught, Missed or Can't tell mark per report (`pilot_checks`, append-only). It is a plain page in the widget's look, not part of the widget bundle, and must never be linked from a public page.

**`buildApp()` in `src/app.ts` is separate from `server.ts`** so route tests `inject()` requests with no port or browser. Storage (`src/storage/`) is `node:sqlite` and opt-in: every route works without a database. `GET /api/storage` reports whether `DB_PATH` is durable.

**Fixture detection tests.** `backend/test/fixtureDetection.test.ts` scans `backend/public/qa-*.html` over `file://`. Each fixture holds known defects beside sections built to be correct, and several exist to prove a silence. A new probe needs one of these, not only unit tests.

**Widget internals.** `App.tsx` owns the scan flow and report state. `src/api/` holds the scan and chat clients. Reader-facing copy lives in `src/lib/strings.ts` with `strings.{de,es,fr}.ts` beside it, and WCAG plain-language text in `wcagPlain*.ts`. The language is a module-level value in `lib/i18n.ts`, read at render time, not React context; English is the fallback for any missing key. Tests in `widget-business/test/` enforce voice and honesty rules on that copy (`voice.test.ts`, `voice.de.test.ts`, `chatHonesty.test.ts`, `researchLines.test.ts`). A copy change that trips them is usually the copy's fault. `ACCESSIBILITY.md` is the widget's own audit against WCAG.

Comments in this codebase are long and record what was measured and why a value is what it is. Read them before changing a number such as a timeout, a limit, or a concurrency value.

Light keeps its values (`#f0efe8` tiles, white fills, black pills, the marker-yellow hover, black solids); dark is `#1c1c1e` tiles, `#2c2c2e` fills, `#636366` for black pills and anything solid in ink (primary action, chosen option, switch on, rounds; white text 6.1:1), `#3a3a3c` hover with white text, and the highlights take the dark orange `#ff9f0a`, blue `#409cff`, green `#30d158`, yellow `#ffd60a` and pink `#ff375f`, black text on each at 7.4:1 or better. Nothing turns white or cream in dark. A new pinned colour goes through these tokens, never a literal. **Controls in dark are fills, not outlines** (same day, "design this"): a button, a choice and the language menu are `#2c2c2e` with no visible edge (the base button rule reads `--btn-fill`, set only in dark), the chosen choice and the primary action `#636366`, hover `#3a3a3c`; a disabled control keeps its dashed ink edge; text fields are `#1c1c1e` with a 1px `#8e8e93` edge (`--field-edge`, `--field-bg`), Block `DARK CONTROLS AS FILLS` at the end of `global.css`.
- Every border, outline and rule is `var(--ink)`. A surface is paper or ink; text on it is the other one (21:1). A dark slab with light text is allowed (`.a11y-section-tint`, `.a11y-pro-scorecard`, the failing stat tile); a slab whose text depended on a mid-grey is paper with a 2px ink edge.
- **What colour used to say is said by shape.** Severity: Fix first is solid ink; Fix soon is a solid 2px edge on paper; Fix eventually is dashed; Minor polish is dotted. The legal marks follow the same ladder. The score dial is a solid arc on a dotted track, the meter a solid bar with ticks at 70 and 90. A disabled control is a dashed edge on paper, never faded (fading is grey). Focus is the dark-green exception below. Pictures of the customer's page are `grayscale(1)`; the vision simulator is exempt because its colour is the point.
- **The opening questions are tiles (user's instruction and reference, 17 Nov 2026, replacing the 4 Nov display questions and their four hover colours):** one tile per group on an auto-fit grid (min 260px, 10px gutter), 20px corners, the fixed `#f0efe8` ground with black words in both themes; the group label top-left at 15px Medium, the question at the foot at 30px. **No longer square (user's instruction, 18 Nov 2026, "less tall, text 20% smaller, it gets cut off"):** a 200px floor that grows with the words, the question 38→30px and the label 18→15px. **30% taller (user's instruction, later on 18 Nov 2026):** the floor is now 370px, 1.3 times the roughly 280px the longest question set on a desktop; phones keep no floor. Then the question **30% smaller**, 30→21px at +0.01em and line-height 1.15. On a phone they follow the phone layout below. The whole tile is the button; hover and focus turn it solid black with white words and a 1px white edge, and show a white "Ask this" pill. Disabled is a dashed edge. **Since 18 Nov 2026 they are tall cards** (user's reference, measured on a font site): the 296:407 proportion instead of the 370px floor, 26px padding, 25px gutter on an auto-fit grid (min 240px); the group as the card's name top-left at 22px Medium, the question under it at 18px/1.3; the "Ask this" pill bottom-right. Their grey ground and New/Update badges are left out. Phones keep the sideways row. **At the card's foot stands the WCAG criterion the question checks** (user's choice, 18 Nov 2026, replacing a 180px question mark that "looks like slop"): tabular figures at the question's own size and ink, 15px Regular (19px on a phone), with no highlight since 21 Nov 2026 (user's instruction, "make this normal size and delete background"; it was 34px Medium on the orange rule-id highlight). It is its own button: pressing it puts "What does WCAG x ask for?" and the criterion's number, name, level and plain question into the thread at once, from `lib/promptCriteria.ts`, with no request to the assistant. That table copies the backend's conformance names and plain questions (all four languages), so the card and the report agree. Help me questions and the manual test plan check no single criterion and show no number. The card is a frame holding two buttons; the question's `::after` stretches over the card. `keepFocusClear` scrolls only for keyboard focus (`:focus-visible`), because scrolling on a press moved the number out from under the pointer and the click never landed.
- **Focus is dark green (user's instruction, 18 Nov 2026, "make focus outline dark green").** A 2px line of `--focus` (`#198038`) inside the element's own edge (`outline-offset: -2px`), square to its corners, with no paper ring and no gap; links take it 2px outside so it never cuts letters. It is the one colour outside the highlights. In light it measures 5.0:1 on white, 4.35:1 on `#f0efe8` and 3.9:1 on marker yellow. Dark mode's greys are too close to it (1.2:1 on the `#636366` solids), so dark takes a lighter green, `#6fdc8c` (3.5:1 on `#636366`, 8:1 on `#2c2c2e`), set with the other dark tokens on `.a11y-widget-biz`. The colour census should allow `rgb(25, 128, 56)` and `rgb(111, 220, 140)` on outlines only.
- Before adding a colour, a grey or an `opacity`, stop: there is nothing to add it to. To check a change, run the colour census (every computed colour in every state, light and dark, must be black, white or transparent) and a text-on-ground measurement; both were zero-failure when this rule was written.
